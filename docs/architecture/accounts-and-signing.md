# Accounts and Signing

Sapient supports two kinds of account side by side, switchable from the same account list, both
implementing the same interface so the rest of the codebase (background message handling,
transaction execution, the popup UI) doesn't need to know or care which kind is active.

```ts
// src/lib/accountApi.ts
export interface WalletAccountApi {
  getComponentAddress(): Promise<string>;
  getWalletAddress(): Promise<string>;
  getBalances(): Promise<TokenBalance[]>;
  getProvider(): Promise<IndexerProvider>;
  execute(instructions: Instruction[], opts?: TransactionExecuteOpts): Promise<unknown>;
  send(recipientAddress: string, resourceAddress: string, amount: bigint, maxFee?: bigint): Promise<unknown>;
  claimTestnetXtr(): Promise<unknown>;
}
```

## `OotleAccount` — local, seed-derived

The default kind. Holds real key material (derived from the wallet's own recovery phrase) and
signs and submits directly to the network — no daemon involved at any point.

**Seed and derivation are byte-exact ports of Tari's own official formats**, not a custom scheme:

- The 24-word recovery phrase is a real `CipherSeed` (`src/lib/cipherSeed.ts`) — version, birthday,
  16-byte entropy, and a MAC, ChaCha20-encrypted with an Argon2d-derived key (46 MiB memory cost),
  CRC32-checksummed. This reproduces `base_layer/common_types/src/seeds/cipher_seed.rs` from the
  Tari codebase directly.
- Account keys are derived with Ootle's own `derive_ristretto_key` (`src/lib/derivation.ts`): a
  domain-separated Blake2b-512 hash under `KeyManagerDomain`, wide-reduced to a Ristretto scalar,
  reproducing `crates/wallet/crypto/src/derive.rs`.
- The on-chain component address is derived client-side (`src/lib/componentAddress.ts`) — a
  domain-separated Blake2b-256 hash of the account template address and the owner public key,
  reproducing `derive_component_address_from_public_key` from `tari-ootle`'s engine crate, since
  neither the published `@tari-project/ootle` nor `@tari-project/ootle-wasm` expose this
  computation.

**Practical consequence**: a recovery phrase created here imports into the official wallet
daemon/Aurora/desktop wallet, and phrases from those import here — every one of these derivations
was checked against real golden vectors generated by the actual upstream Rust crates, not just
self-consistency.

`OotleAccount.execute()` (`src/lib/wallet.ts`) is the core transaction-building entry point every
account operation ultimately goes through. See
[Transaction Lifecycle](transaction-lifecycle.md) for what it actually does — it's more than a
thin wrapper over "sign and submit," because of a gap in how substate dependencies get resolved
client-side.

## `DaemonAccount` — relayed through `tari_ootle_walletd`

Connects to a locally- or remotely-running wallet daemon and relays every operation to it. The
daemon holds the real key material; this class never signs or derives anything itself. Two
consequences that make it a genuinely different code path, not just a swapped-in signer:

- **No client-side retry loop.** The daemon's `transactions.submit` JRPC method takes a
  `detect_inputs: true` flag that does the same substate-dependency discovery `OotleAccount.execute()`
  has to do reactively (see [Transaction Lifecycle](transaction-lifecycle.md)) — server-side, in one
  round trip. `DaemonAccount.execute()` just builds the unsigned transaction and submits it once.
- **Authenticates with a long-lived API key, not a session.** The daemon's normal browser login
  flow relies on an `HttpOnly`, `SameSite=Strict` cookie a `chrome-extension://` origin can never
  hold, and its WebAuthn default locks its origin to `http://localhost:{port}`, which an extension
  page never runs on either. The only path that actually works from here is a long-lived API key,
  minted once from the daemon's own web UI and pasted into the connect screen. The key must carry
  the `admin` permission — checked at connect time, since a narrower key is rejected by this
  wallet's own daemon-relayed testnet-XTR claim regardless.

**Known limitation**: stealth/confidential operations aren't wired up for daemon accounts.
Everything this wallet actually does with a Stealth-typed resource (claim, send, swap) for a local
account moves it through revealed `withdraw`/`deposit`, which needs no stealth signing — the
daemon's own stealth JRPC exists but isn't called here. HTLC funding
([Stealth Balances and HTLCs](stealth-and-htlc.md)) is local-account-only for the same reason:
building a `PayTo::Conditions` stealth output witness needs the account's own stealth crypto, which
only `OotleAccount` has.

## Account resolution and caching

`background/accounts.ts` resolves a stable account id (`local:<index>` or
`daemon:<connectionId>:<componentAddress>`) to a live `WalletAccountApi` instance, and caches the
result — both kinds hold a live network connection, so repeated calls within one unlocked session
reuse it rather than reconnecting every time. The cache is cleared on lock, wallet reset, and
network switch (a stale daemon-relayed account must not keep talking to the old network).

Resolving *any* account — local or daemon — requires the wallet to be unlocked: a daemon
connection's own API key is itself encrypted at rest with a key derived from the seed (see
`secretAtRest.ts`), so it's unusable without an unlocked seed either way. This turns what would
otherwise be a confusing decrypt failure into a clean "wallet is locked."
